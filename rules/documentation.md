# 项目文档规范(跨域:需求到验收全生命周期)

适用:所有业务项目的过程文档。文档与代码同仓、随 git 走,禁止散落在网盘/聊天记录/仓库根目录。

## 目录结构(MUST)

```text
docs/
├── requirements/     # 需求文档:REQ-001-user-login.md
├── proposals/        # 项目方案/技术方案:PROP-001-xxx.md(spec-generator 产出也归这里)
├── plans/            # 开发计划:PLAN-001-xxx.md(阶段、时间线、里程碑)
├── tasks/            # 任务分解与进度:TASK-001-xxx.md(状态列即进度追踪,不单设进度目录)
├── testing/          # 测试标准与用例:TEST-001-xxx.md
├── acceptance/       # 验收标准与记录:ACC-001-xxx.md
├── api/              # API 契约(openapi.yaml,遵循 rules/collaboration.md)
└── migrations/       # 数据库迁移脚本(遵循 rules/database.md)
```

1. 每类文档只能出现在自己的目录;找文档按生命周期阶段定位,禁止跨目录混放。
2. 目录与文件名用英文 kebab-case,文档标题与正文用中文。
3. 编号规则:`{前缀}-{三位序号}-{英文短名}.md`;序号目录内唯一、递增、**永不复用**(文档废弃保留编号并标状态)。

## 通用头部元信息(MUST)

每篇文档开头固定放置:

```markdown
# {编号}:{中文标题}

> 一句话摘要:{业务人员能看懂的一句话}

| 编号 | 状态 | 创建日期 | 最后更新 | 作者 | 关联文档 |
|------|------|---------|---------|------|---------|
| REQ-001 | 已确认 | 2026-08-09 | 2026-08-09 | 张三 | PROP-001、TASK-001 |
```

1. 状态流转:`草稿 → 评审中 → 已确认 → 已归档`;**已确认文档的实质性变更必须重新评审**,并在文末「变更记录」表追加(日期/变更内容/原因/评审人)。
2. 关联文档双向填写:需求列出它的方案与任务,方案回指需求。

## 写作规范(MUST)

1. **大白话优先**:面向的读者是「不懂技术的业务人员也能看懂」;先说人话,再补技术细节。
2. **术语必须注释**:专业术语首次出现用括号解释,如「幂等(同一操作执行多次,结果和执行一次相同)」;单篇术语超过 5 个时文末附术语表。
3. **禁止模糊表述**:「大概、尽量、看情况、优化一下、体验更好、越快越好」等不可验证的措辞禁止出现在需求、任务、验收文档中——每条内容必须能回答「怎么算做完了/达标了」。
4. 能用列表和表格不用长段落;一段只说一件事。
5. 涉及流程用步骤列表或流程图,涉及取舍用对比表。

## 追溯(MUST)

1. 方案必须引用需求编号;任务必须引用需求(或方案)编号;测试用例必须引用需求编号;验收必须按需求编号逐条对照。
2. 无编号引用的方案/任务/用例视为不合规,评审阻断。
3. 追溯链:`REQ → PROP → PLAN → TASK → TEST → ACC`,从任一需求可以顺藤摸瓜查到验收结果。

## 各文档类型必备章节(MUST)

### requirements/(需求)

背景(为什么做,业务语言)→ 目标(可验证,如「客服处理时长从 10 分钟降到 3 分钟」)→ 使用场景(大白话讲「谁在什么情况下做什么」)→ 功能清单(P0/P1/P2 分级,每条子编号如 REQ-001.1)→ 非功能要求(性能/安全/兼容,仅列实际有的)→ **明确不做的事** → 每条功能的验收口径 → 开放问题(待确认项 + 责任人)。

### proposals/(方案)

关联需求 → 方案对比(1~3 个,优缺点 + 结合上下文的推荐理由)→ 选定方案(架构图、模块划分、关键技术决策)→ 对需求的覆盖对照(每条 REQ 由哪个模块承接)→ 风险与对策 → 里程碑概览。技术规格类内容可由 `spec-generator` skill 生成后归入本目录。

### plans/(开发计划)

阶段划分(每阶段:目标、交付物、依赖)→ 时间线(里程碑日期)→ 人员与分工 → 计划变更记录(变更必须写原因)。

### tasks/(任务与进度)

任务表为主体,**状态列就是进度追踪**,不另写进度周报:

| 任务编号 | 描述 | 关联需求 | 负责人 | 估时 | 状态 | 完成标准(DoD) |
|---------|------|---------|--------|------|------|---------------|
| TASK-001.1 | 登录接口 | REQ-001.1 | 张三 | 2d | 进行中 | 接口通过测试用例 TEST-001.1 |

1. 状态取值:`待开始 / 进行中 / 阻塞 / 已完成(附日期)`;阻塞必须写原因与等待的依赖。
2. 每条任务必须有可验证的完成标准(DoD),禁止「开发完成」这类空话。
3. 状态在评审节点与里程碑时必须刷新,过期状态视为失真。

### testing/(测试标准)

测试范围与环境 → 用例表(用例编号/关联需求/前置条件/操作步骤/预期结果/实际结果)→ 通过标准(如「P0 用例 100% 通过,整体 ≥ 95%」)→ 执行方式遵循 `rules/testing.md`。

### acceptance/(验收)

按需求编号逐条:验收动作(照着做一遍的步骤)→ 预期结果 → 实际结果(通过/不通过 + 截图或数据证据)→ 遗留问题(责任人 + 解决期限)→ 验收结论(通过 / 有条件通过 / 不通过)。

## 与代码规范的衔接

1. API 契约放 `docs/api/`,格式遵循 `rules/collaboration.md`;数据库脚本放 `docs/migrations/`,遵循 `rules/database.md`。
2. PR 描述引用任务编号(TASK-xxx),让代码变更也进入追溯链。
