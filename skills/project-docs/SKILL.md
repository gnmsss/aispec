# 项目过程文档

## 编写引导

1. 任何过程文档任务,先读 `rules/documentation.md`(目录结构、编号、元信息、写作规范、各类型必备章节)。
2. 流程:
   - 确认文档类型 → 定位目录(requirements/proposals/plans/tasks/testing/acceptance)
   - 查目录内现有编号,取下一个序号(编号永不复用)
   - 按该类型「必备章节」组织内容,头部放统一元信息表 + 一句话摘要
   - 填写关联文档编号(追溯强制:方案引需求、任务引需求、用例引需求、验收逐条对需求)
3. 更新进度时:直接改 `tasks/` 文档的状态列(待开始/进行中/阻塞+原因/已完成+日期),不新建进度文档。
4. 技术规格类方案配合 `spec-generator` skill 生成,产出归入 `docs/proposals/`。

## 写作自查(输出前必过)

1. 一句话摘要业务人员能看懂;正文先人话后技术。
2. 专业术语首次出现有括号注释;术语 >5 个有术语表。
3. 无「大概/尽量/看情况/优化一下」类模糊词;每条内容可回答「怎么算做完了」。
4. 优先列表与表格;一段只说一件事。

## 文档审查清单

违反 MUST 项标记为不合规:

1. 位置:文档在正确目录;命名 `{前缀}-{三位序号}-{英文短名}.md`;编号未复用
2. 元信息:头部表完整(编号/状态/日期/作者/关联文档);已确认文档的变更有变更记录
3. 追溯:方案/任务/用例/验收均有需求编号引用;验收按 REQ 逐条对照
4. 明确性:需求每条有验收口径;任务每条有 DoD;无模糊表述
5. 大白话:摘要与背景无未注释术语;读者不懂技术也能理解在做什么
6. 章节:该类型必备章节齐全(含「明确不做的事」「开放问题」等易漏项)
7. 状态:tasks 状态列与实际一致;阻塞项写了原因与依赖

## 初始化脚手架

新项目初始化文档体系时:建 `docs/{requirements,proposals,plans,tasks,testing,acceptance,api,migrations}/` 八个目录,各放一篇 `TEMPLATE.md`(按 `rules/documentation.md` 对应章节的空模板),并在项目 README 注明「文档找什么去哪个目录」对照表。
